# DanaConnect — платформа менторства

Платформа создаётся с нуля по плану и брендбуку, предоставленным владельцем. Реализованы основные процессы менти и ментора, отдельная админ-панель, адаптеры доставки, расписания, командная работа, материалы и достижения. В третьей фазе добавлен код уведомлений/следующих шагов, поддержки, управления членством команды, статусов прочтения и ручного экспорта календаря. Подготовлена облачная конфигурация.

**Опубликовано в Vercel: [сайт](https://danaconnect.vercel.app), [отдельная админка](https://danaconnect.vercel.app/admin).** Production deployment сообщил READY; API `/api/v1/ready` вернул HTTP 200 и `ready`. Подключены чистая Neon PostgreSQL и private Blob, Gmail SMTP настроен, QStash подтвердил активное расписание каждые две минуты. Google OAuth credentials и импорт MFA владельцем ещё не подтверждены; доставка писем, операции с файлами и пользовательские сценарии не проходили функциональную приёмку. Демонстрационные профили и документы не являются данными реальных участников или утверждёнными юридическими текстами. Точные факты: [подключение среды](docs/ACTIVATION_STATUS.md).

## Что входит

| Область | Реализация |
|---|---|
| Вход и анкеты | Email OTP, HttpOnly cookie, роли менти/ментор, согласия с актуальными версиями документов, модерация и повторная проверка существенных изменений |
| Безопасность администратора | Отдельное приложение; роль проверяется сервером, production вход требует TOTP MFA; первоначальная настройка только операторской командой |
| Проекты и менторство | Каталог, проекты, заявки и прямой запрос ментору, вместимость, участие, пауза/возобновление, успешное и досрочное завершение |
| Коммуникация | Личные диалоги, счётчики непрочитанных, отдельные receipts показанных входящих сообщений, ранние страницы; комментарии с причиной модерации, приглашения, список собственных команд, self leave/removal collaborator и приватные вложения |
| Уведомления и поддержка | `/notifications`: непрочитанные/все, пагинация, read-one/read-all и следующие шаги; `/support`: свои обращения, приватные ответы и пояснения решений. Общие обращения доступны до одобрения профиля |
| Ограничения отправки | До 20 сообщений и до 20 комментариев в минуту на пользователя, со свежей проверкой доступа и audit в транзакции |
| Календарь | Разовые и еженедельные слоты, IANA/DST, бронирование, отмена, ссылка, неявка/проведение; worker для напоминаний/outbox; приватный ручной ICS-снимок своих встреч без автоматической синхронизации |
| Результаты | Подтверждение результатов, добровольные отзывы/NPS, витрина с согласиями, аналитика и CSV |
| Развитие | Материалы по направлениям, прозрачные правила баллов/значков, добровольный рейтинг, административные награды и PDF сертификатов платформы |
| Дополнительные интеграции | Resend/SMTP, Google sign-in, AI-помощь с согласиями и лимитами; включаются только после настройки реальных провайдеров |
| Управление | Участники и статусы, анкеты, проекты, направления, документы/переводы/версии, комментарии, обращения и ответы, privacy queue, audit, результаты, состояние сервисов и admin `/launch` для подготовки пилота |
| Языки | Интерфейс RU/KZ/EN; пользовательские тексты остаются в исходном языке, отсутствующий перевод документа/материала явно возвращается к оригиналу |

Наличие реализации не означает, что внешние сервисы уже подключены или весь пилот принят. Подробности и evidence: [состояние реализации](docs/IMPLEMENTATION_STATUS.md).

Для выбранного размещения на Vercel подготовлены закрытая конфигурация, отдельное обновление внешней PostgreSQL, переносимый шрифт сертификатов и упаковка исходников с контрольными суммами. [Подготовка выпуска](docs/RELEASE_PREPARATION.md). Эти инструменты не создают облачные ресурсы и не подтверждают публикацию.

Админка `/operations` показывает снимок очереди писем, задержки и состояние worker, позволяет вручную обновить и скачать ограниченную диагностику. Ошибки API получают собственный Request ID для поиска безопасной записи HTTP в журнале. [Инструкция оператору](docs/MONITORING_RUNBOOK.md). Внешние alerts и контроль расходов пока не подключены.

**Третья фаза:** главный агент подтвердил компиляцию API, TypeScript обоих frontend и применение миграции `0e82eab8e5ef` (`report_responses`/`message_reads`) с head на локальной SQLite после копии БД. Обе полные сборки прошли, exit 0: web 22 записи маршрутов, admin 19, включая not-found. Standalone frontend сообщили Ready на 3000/3001, API — startup complete на 8000. Worker запущен без настроенной почты, операций нет. Это не приёмка сценариев или production PostgreSQL.

## Локальный запуск на Windows

Требуются Python 3.12+ и Node.js 22. Из корня проекта:

```powershell
.\scripts\setup.ps1
```

Скрипт создаёт окружение, устанавливает зависимости API, сайта и админ-панели, копирует отсутствующие `.env` из примеров и применяет миграции. Существующие настройки и записи сохраняются. **Вымышленные данные добавляются только явно:**

```powershell
.\scripts\setup.ps1 -Demo
```

Локальный пример API включает режим разработки и отладочные коды. Эти настройки нельзя переносить в production. `app.seed` допускается только в development с `DEMO_MODE=true`; автоматически при старте API данные не создаются.

Четыре отдельных терминала:

```powershell
.\scripts\dev.ps1 -Service api
.\scripts\dev.ps1 -Service web
.\scripts\dev.ps1 -Service admin
.\scripts\dev.ps1 -Service worker
```

| Сервис | Локальный адрес |
|---|---|
| Сайт | `http://127.0.0.1:3000` |
| Отдельная админ-панель | `http://127.0.0.1:3001` |
| Документация API | `http://127.0.0.1:8000/docs` |
| Worker | Отдельный процесс без публичного порта |

Локальная SQLite не требует сервера. `compose.dev.yml` содержит необязательный PostgreSQL для разработки. Production использует постоянный PostgreSQL и приватное объектное хранилище. Подробнее: [миграции](apps/api/migrations/README.md).

Для локального preview **уже собранных** сайта и админки выполнить `npm run start` отдельно в `apps/web` и `apps/admin`. Общий `scripts/serve-next.mjs` копирует `public` (если есть) и `.next/static` в standalone output и запускает `server.js` на `127.0.0.1:3000/3001`. Предварительная сборка обязательна; launcher не выполняет build/install. Публичный контейнерный запуск описан в cloud runbook.

## Почта, worker и дополнительные интеграции

- Почта: `EMAIL_PROVIDER=resend` или `smtp`, проверенный `EMAIL_FROM` и соответствующие credentials. Код ставится в зашифрованную outbox; отправка требует работающего worker. Статус `queued` не означает доставки.
- Worker: `python -m app.jobs_calendar --interval 60` из `apps/api`; однократный цикл — `--once`. Он поддерживает горизонт расписаний, напоминания и очередь писем. Не запускать два разных расписания обработки одновременно.
- Google: `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, корректный HTTPS `GOOGLE_REDIRECT_URI`; доступность определяется backend. Live OAuth в текущем окружении не проходился.
- AI: по умолчанию выключен. Нужны `AI_ENABLED=true`, `AI_API_KEY`, выбранный `AI_MODEL` и бюджет/лимиты. Реализованы структурирование черновика, объяснимый подбор доступных менторов и рекомендации администратору. Отправка требует явного согласия; AI не одобряет анкеты и не меняет доменные данные автоматически. Без провайдера возвращается состояние недоступности.
- Приватные файлы: локальный каталог допустим только для разработки. На Vercel подключён private Blob; для контейнерного размещения предусмотрен S3 через стандартную AWS credential chain. Доступ к скачиванию проверяется API, публичные ссылки на хранилище не выдаются.

## Облачный запуск

Платформа опубликована на Vercel: сайт `/`, отдельная админка `/admin`, API `/api/v1`. Подключены Neon PostgreSQL, private Blob, Gmail SMTP и QStash с расписанием каждые две минуты. Актуальные ограничения и подтверждения подключения описаны в [ACTIVATION_STATUS.md](docs/ACTIVATION_STATUS.md).

Подготовлены Dockerfiles трёх приложений, `compose.prod.yml`, TLS proxy, отдельный worker, постоянные volumes PostgreSQL, скрипты приватной конфигурации, backup и восстановления в новую отдельную БД. Для Vercel предусмотрены Services и отдельный opt-in минутного cron; default config не включает cron. Нельзя обещать своевременные OTP/напоминания с дневным расписанием.

Полная последовательность подключения ресурсов и запуска: [CLOUD_RUNBOOK.md](docs/CLOUD_RUNBOOK.md). Контейнерный запуск, S3, доставка писем, восстановление backup и внешние AI-вызовы не проходили функциональную приёмку.

## Проверки и границы evidence

В ранней локальной фазе **1 октября 2026 года, до текущего расширения**, ранее прошли 43 серверных теста на временных SQLite-базах, сборка сайта и ограниченные браузерные сценарии. Это историческая evidence базовых функций; она не подтверждает новые модули или production PostgreSQL.

**Исторический итог второй фазы, 1–2 октября 2026 года:** обе общие frontend-сборки прошли компиляцию, TypeScript и генерацию страниц: сайт — 20 маршрутов, включая `/recommendations`, админка — 18, включая `/activity` и `/ai-review`. Миграция дополнительных модулей применена к локальной SQLite; API и worker стартовали локально. Worker обработал 0 писем, почтовый провайдер не настроен. Открыта страница входа админки для ограниченного preview без отправки формы. Это не проверка новых маршрутов и таблиц третьей фазы. Тесты и функциональные браузерные сценарии во второй и третьей фазах не запускались; сборка/старт/preview не подтверждают работу всех процессов и внешних сервисов.

`scripts/check.ps1` включает существующий API test run, TypeScript и сборки сайта **и отдельной админ-панели**. В `.github/workflows/check.yml` добавлено отдельное задание admin с собственным lockfile и сборкой `/admin`. При этом обновлении ops определения тестов не добавлялись и не менялись; скрипт/CI после обновления не запускались, внешний CI run не подтверждён. Не собирать приложение одновременно с его `next dev` — они используют один `.next`.
