# Наблюдение и диагностика DanaConnect

**Фаза 5, 2 октября 2026 года.** Руководство описывает предусмотренную диагностику в коде. Функциональные проверки этой фазы и подключение production-провайдеров не выполнялись; облачный выпуск пока не подтверждён.

## 1. Где смотреть состояние

В отдельной админке открыть **Операции**: локально `/operations`, в облаке с префиксом — `/admin/operations`. Нужна действующая сессия администратора; production-вход требует настроенной MFA. Данные поступают из защищённого API `GET /api/v1/admin/operations`.

- **Обновить** запрашивает новый снимок; автоматического опроса и внешних оповещений нет.
- **Скачать диагностику (JSON)** сохраняет ограниченный набор показателей текущего снимка. Экспорт исключает адреса получателей, тексты писем, секреты и персональные записи. Это диагностика, не резервная копия базы.
- Сначала сверить время `observed_at` в UTC. Снимок описывает состояние при запросе и может устареть после загрузки.

Расчёты возраста используют одно время UTC запроса, но отдельные чтения БД не являются атомарным журналом доставки: работающий worker может изменить очередь между ними.

Страница и экспорт доступны для чтения. Они не отправляют письма, не запускают worker и не возвращают записи в очередь.

Публичные `/api/v1/health` и `/api/v1/ready` имеют более узкий смысл: первый отвечает о процессе и режиме, второй выполняет запрос к БД. Успешный ответ не подтверждает очередь, полную схему/миграции, S3, доставку письма, PDF, MFA или восстановление backup. Наличие настроек в `readiness` тоже не является проверкой прав и подключения внешнего сервиса.

## 2. Как читать очередь писем

`delivery.status_counts` содержит число записей в каждом текущем состоянии:

| Состояние | Значение |
|---|---|
| `pending` | Ожидает попытки, включая отложенный retry; не вся очередь готова к отправке сейчас |
| `leased` | Worker взял запись на ограниченное время; это не подтверждение отправки |
| `sent` | Провайдер принял отправку, либо явно выбранный локальный console завершил обработку; получение во входящих не подтверждено |
| `failed` | Обработка завершена с кодом причины; сюда также входят намеренные отмены |

Дополнительные поля помогают отличить задержку от планового ожидания:

| Поле | Значение |
|---|---|
| `due_pending` | `pending` с наступившим `next_attempt_at` и ещё действующим сроком письма |
| `expired_pending` | Ожидающие письма с истёкшим сроком; своевременная отправка уже невозможна |
| `expired_leases` | `leased` с истёкшим либо отсутствующим `lease_until`; worker может повторно захватить их |
| `oldest_pending_at` | Самая ранняя дата создания среди всех `pending`, включая отложенные и просроченные |
| `oldest_due_at` / `oldest_due_age_seconds` | Самое раннее время наступившей попытки и задержка для действующих `due_pending`; отсутствие такой записи даёт пустое значение |
| `failures_last_24h` | Текущие `failed`, созданные за последние 24 часа до снимка; это **не** число переходов в отказ за 24 часа, поскольку отдельная дата отказа не хранится |
| `failure_codes` | Группы кодов всех текущих `failed`, независимо от времени создания |

Показатели не содержат payload, адреса, ID писем или ответ провайдера. Статусы являются снимком БД; они не описывают размер входящих почтовых ящиков, bounce/spam или число уникальных получателей. Индикатор `email_failed` исключает штатные `booking_cancelled` и `invitation_revoked`, а счётчик `failed` и группы кодов сохраняют их: несовпадение здесь ожидаемо.

## 3. Коды отказов и первый шаг оператора

| Код или группа | Что выяснить до повторной обработки |
|---|---|
| `provider_unconfigured` | Совпадают ли настройки API и worker; выбран ли провайдер, задан ли отправитель и credentials |
| `resend_network`, `smtp_connection` | Доступность сети, DNS/TLS и сервиса со стороны worker |
| `resend_http`, `smtp_response` | В защищённой панели провайдера найти соответствующий отказ: лимит, авторизация, отправитель или временная ошибка. Точные числовые HTTP/SMTP коды объединены в группе |
| `resend_invalid_response`, `provider_missing_receipt` | Принял ли провайдер письмо; отсутствующая квитанция не доказывает, что отправки не было |
| `smtp_recipient_refused` | Причину отказа адресату у провайдера; адрес не показывается в диагностике платформы |
| `payload_decryption_failed` | Согласованность текущего и предыдущих ключей outbox у API/worker. Не заменять ключ вслепую и не удалять очередь |
| `attempts_exhausted` | Первопричину предыдущих попыток по защищённым журналам и состоянию провайдера; лимит уже исчерпан |
| `message_expired` | Тип и срок действия сообщения. Истёкший OTP нельзя превращать в действующий повторной отправкой |
| `booking_cancelled`, `invitation_revoked` | Штатную отмену встречи или отозванное приглашение; повторная отправка старого сообщения не нужна |
| `delivery_unexpected`, `other` | Версию приложения, состояние БД/worker и безопасные диагностические события; произвольный текст ошибки в API не выводится |

Группы не показывают подробность всех причин. `other` включает неизвестные, пустые и неподдерживаемые значения; это не подтверждение отсутствия ошибки. Исходные ответы провайдера и приватные настройки изучает оператор с соответствующим доступом, без публикации их в чат или support-экспорт.

## 4. Состояние worker

Heartbeat хранится в одной записи `calendar` и обновляется при цикле. Это последний известный цикл, а не список процессов на всех хостах.

| Сигнал | Как читать |
|---|---|
| Нет heartbeat / `worker_missing` | Ни один цикл ещё не зарегистрирован в этой БД. Это отличается от известного, но устаревшего worker |
| `status=running` | Зарегистрировано начало цикла. Завершение текущего цикла ещё не подтверждено; старое `last_finished_at` может относиться к предыдущему |
| `worker_running_long` | Текущий `running` длится не менее 5 минут; выяснить, выполняется ли процесс, завис ли вызов или оборвалось завершение |
| `status=failed` / `worker_failed` | Последний цикл записал ошибки генерации правил/напоминаний; просмотреть безопасные счётчики и журналы |
| `worker_stale` | Возраст завершения не менее 5 минут либо для неработающего состояния завершение отсутствует. Для `running` с отсутствующим временем начала также показывается этот сигнал: возраст неизвестен |
| `status=success` / `recent_success=true` | Последний цикл завершён без записанных ошибок календарных этапов и достаточно недавно. Почта при этом может быть `unconfigured` или содержать `failed` |

`age_seconds` — возраст последнего завершения; `running_age_seconds` — возраст начала текущего `running`. `duration_seconds` показывает только согласованную пару начала/завершения завершённого цикла. Пустое значение означает отсутствие подходящих данных, а не нулевую задержку. Для `running` с известным началом показывается отдельный сигнал долгого выполнения, без дополнительного `worker_stale`.

В `summary` доступны только фиксированные счётчики этапов `rules`, `reminders`, `email` последнего завершённого batch. Пока следующий цикл `running`, сохраняется предыдущий summary; это не текущий прогресс. Нули могут означать отсутствие работы в завершённом batch. `email.status=unconfigured` нужно рассматривать отдельно от общего `success`. `in_app_only` подтверждает создание внутреннего напоминания без очереди email, а не доставку письма.

## 5. Порядок реагирования

Пороги **15 минут** для самой старой действующей попытки email и **5 минут** для worker — операторские индикаторы внимания. Они не являются SLA, автоматическим разрешением пилота или гарантией времени OTP. Истёкшие письма, отказанные записи и leases показываются отдельно, без ожидания 15 минут.

1. Обновить снимок и сохранить время, код сигнала, счётчики и версию выпуска. Если требуется передать диагностику — использовать предусмотренный JSON, проверить получателя и доступ к нему.
2. Выяснить область проблемы: недоступен API/БД, не запускается worker, задержана очередь или отказал провайдер. Сравнить heartbeat, конфигурационные флаги и коды отказов; не делать вывод только по `success`.
3. Исправить установленную причину: настройки, сеть/права, выбранный scheduler или конкретную ошибку приложения. У API и worker должны совпадать БД и ключи. Не запускать второй постоянный scheduler поверх уже работающего.
4. После устранения причины оператор может явно возобновить существующий worker либо выполнить его предусмотренный ограниченный цикл `python -m app.jobs_calendar --once` в настроенном окружении. Это действие обрабатывает очередь и изменяет БД; страница мониторинга его не выполняет. Защищённый scheduler endpoint также выполняет работу и не является health-запросом.
5. Получить новый снимок и проверить движение ожидающих записей, свежесть heartbeat и новые отказы. Уже терминальные `failed` не возвращаются в очередь автоматически. Для нового OTP/приглашения использовать соответствующий актуальный пользовательский процесс с его ограничениями и сроками.

Обработка email имеет семантику «как минимум один раз». Resend получает стабильный idempotency key; SMTP получает стабильный Message-ID, который не обеспечивает дедупликацию у провайдера. При обрыве между отправкой и записью результата повторная попытка способна дать дубликат. Не повторять все сообщения вручную, не сбрасывать attempts/leases SQL-командами и не удалять записи для получения зелёного показателя.

## 6. Диагностика HTTP по Request ID

API генерирует собственный `X-Request-ID` для запроса; входной ID клиента не используется как доверенный идентификатор. При проблеме записать время UTC, HTTP-статус и ID из сообщения об ошибке сайта/админки либо response headers в браузере. Показ ID требует ответа сервера; при сетевом обрыве его может не быть. Не передавать cookies, токен, OTP, query-параметры или содержимое приватного запроса.

Искать этот ID в журнале приложения `danaconnect.requests`, событие `http_request`. Поля: `observed_at`, `request_id`, фиксированный `method` либо `OTHER`, доверенный шаблон `route` либо `__unmatched__`, `status_code`, `duration_ms`; `error_kind=server_error` добавляется при исключении. Маршрут представлен шаблоном, например `/api/v1/projects/{project_id}`, без значения ID. Неизвестный путь не копируется в лог.

Необработанная ошибка до отправки headers получает безопасный ответ 500 с ID; после начала streaming-ответа заменить headers уже нельзя. Поэтому обрыв streaming может сохранить `status_code=200` при `error_kind=server_error` — проверять оба поля. Реализация использует pure ASGI middleware: [модель middleware Starlette](https://starlette.dev/middleware/#pure-asgi-middleware).

Этот журнал не сохраняет raw path/query, email, user/IP, headers/body или текст исключения. Отдельные записи не образуют глобальные метрики доступности, latency-percentiles, нагрузочный результат или HA. Request ID не обязательно передаётся дальше в почтовый/S3-провайдер; связь с их журналами оператор устанавливает по времени и доступной защищённой квитанции, без обещания общей трассировки.

Обычный Uvicorn access log отключается в предусмотренных локальных/контейнерных запусках через `--no-access-log`; этот флаг отключает только access log, без смены общего log level: [настройки Uvicorn](https://www.uvicorn.org/settings/#logging). Политики Vercel, proxy и внешних провайдеров настраиваются отдельно: они могут сохранять raw access logs. Ограниченный журнал приложения не доказывает отсутствие персональных данных во всех внешних логах.

## Границы наблюдения

Не подключены внешние alerts, мониторинг расходов, централизованные метрики/трассировка, автоматическое исправление, наблюдение inbox/bounce или гарантии HA. Диагностика конфигурации не подтверждает live PostgreSQL/S3/email, облачную выдачу PDF и backup/restore. Подключение и приёмка остаются отдельными этапами: [подготовка выпуска](RELEASE_PREPARATION.md), [облачный runbook](CLOUD_RUNBOOK.md).
