# План создания платформы менторства с нуля

Дата плана: 1 октября 2026 года. Режим разработки подтверждён пользователем: один разработчик, 25–35 часов в неделю, с помощью Codex. При первоначальном осмотре рабочая папка была пустой. Теперь разработка начата: создана первая локальная версия. Её фактическое состояние отдельно описано в [IMPLEMENTATION_STATUS.md](IMPLEMENTATION_STATUS.md); ниже сохранён полный план продукта.

Создаём веб-платформу, на которой участник регистрируется, получает одобрение, находит ментора или проект, проводит встречи и фиксирует результат. Первым выпуском будет пилот с полным жизненным циклом участия. Затем расширяем продукт ИИ, геймификацией и дополнительными возможностями. Архитектура с первого выпуска поддерживает новые направления через данные.

Для прототипирования используем тестовые данные и временные настройки; до запуска соответствующие вопросы должны получить решение.

## Что меняем в последовательности исходного плана

Админ-панель появляется вместе с регистрацией: без неё нельзя проверять анкеты, активировать пользователей и управлять направлениями. Её расширенная аналитика появляется позже.

Реестр результатов входит в пилот. Без него нельзя завершить участие и проверить главные бизнес-цели. Его схему проектируем до форума и бронирований.

Обязательные согласия, права доступа и защита файлов вводятся до пользовательской активности. ИИ подключаем после появления устойчивых форм и справочников. Обработка заявок сначала ручная, с теми же журналами действий, которые позднее будут использоваться для проверки рекомендаций ИИ.

Каждый этап создаёт работающий сценарий через интерфейс, сервер и базу данных. Промежуточная демонстрация с вымышленными пользователями позволяет проверить бизнес-правила до подключения реальных участников.

## Роли и работа платформы

Гость видит главную страницу, согласованные публичные описания проектов, одобренные профили менторов, направления, витрину и агрегированную отчётность. Заявки, комментарии, закрытые материалы и бронирование доступны после полного допуска. Это предложенное разделение чтения публичных страниц и активного использования из раздела 7.

Менти заполняет анкету, подписывает обязательные документы, получает решение администратора, публикует идею или подаёт заявку, взаимодействует с ментором, бронирует встречи и фиксирует результат. Ментор дополнительно подтверждает экспертизу, задаёт вместимость и расписание, принимает заявки и оценивает результат. Администратор проверяет анкеты и контент, управляет справочниками и версиями документов, рассматривает жалобы и видит отчёты.

| Сущность | Предлагаемые состояния | Правило |
|---|---|---|
| Анкета | Черновик → подана → одобрена либо требует исправлений | Возврат анкеты не удаляет историю проверки |
| Аккаунт | На рассмотрении → активен → приостановлен либо деактивирован | Подтверждение email, актуальные согласия и одобренная анкета нужны одновременно |
| Набор | Открыт либо закрыт | Отдельно от состояния аккаунта; вместимость проверяется на сервере |
| Заявка | Ожидает → принята, отклонена, отозвана или истекла | Отклонение с причиной; принятие не создаёт дубль участия |
| Участие | Активно ↔ приостановлено → завершено успешно либо досрочно | У завершения обязательны структурированный результат и инициатор |
| Встреча | Запланирована → проведена, отменена либо не состоялась | «Не состоялась» — предлагаемое дополнение; проведённость подтверждает ментор |
| Результат | Ожидает подтверждения → подтверждён | Правила защиты и подтверждающего определяет владелец |
| Отзывы | Ожидаются → получены либо срок истёк | Отсутствие ответа не подменяется оценкой 0 |

Самостоятельная работа менти на форуме также может иметь участие без назначенного ментора. Для неё нужно определить, кто подтверждает защиту и какой отзыв обязателен. Консультация до принятия в проект может существовать отдельно от участия; при включении в результат она связывается с ним однократно.

## Предлагаемая техническая основа

Рекомендую один репозиторий с интерфейсом Next.js и TypeScript, сервером FastAPI на Python и PostgreSQL. Все правила допуска, заявок, встреч и результатов находятся в одном серверном приложении, разделённом на модули. Два стека увеличивают объём настройки, поэтому контракт API и общие схемы фиксируются в E1. Это выбранная для планирования основа, её окончательно закрепляем после небольшого технического прототипа.

Файлы хранятся в закрытом S3-совместимом хранилище. Письма и периодические проверки выполняет отдельный worker из того же серверного проекта. Задачи и уведомления записываются в PostgreSQL вместе с бизнес-событием и обрабатываются после фиксации транзакции. Для пилота достаточно очереди в базе с повторными попытками и защитой от повторной отправки. Увеличение числа серверных процессов и отдельный брокер планируем после измерения нагрузки.

| Часть | Решение для планирования | Что должно быть проверено |
|---|---|---|
| Интерфейс | Next.js, TypeScript, адаптивные компоненты и локализация | Мобильные формы, состояния ошибок, три языка |
| Сервер | FastAPI, SQLAlchemy, Alembic | Схемы запросов, миграции, объектные права доступа |
| Данные | PostgreSQL | Уникальность, ограничения, транзакции, резервные копии |
| Авторизация | Email-коды и серверные сессии; Google в R1 | Срок кода, лимиты попыток, безопасное связывание аккаунтов |
| Администрирование | Защищённый раздел того же интерфейса | Отдельные права и усиленный вход администратора |
| Файлы | Закрытое объектное хранилище и ссылки с ограниченным сроком | Права на каждый файл, типы, размеры, проверки загрузок |
| Фоновые задачи | Worker, очередь отправок, планировщик | Повторный запуск не создаёт второе письмо или завершение |
| ИИ | Заменяемый серверный адаптер провайдера | Лимиты затрат, отсутствие лишних персональных данных, отказоустойчивость |
| Развёртывание | Контейнеры, HTTPS, отдельные тестовая и рабочая среды | Секреты, миграции, откат, здоровье сервисов |

Текущие официальные руководства подтверждают возможность самостоятельного размещения [Next.js](https://nextjs.org/docs/app/guides/self-hosting) и описывают вопросы HTTPS, процессов и перезапуска для [FastAPI](https://fastapi.tiangolo.com/deployment/concepts/). Для бронирований и мест предусмотрены транзакции и [блокировки строк PostgreSQL](https://www.postgresql.org/docs/current/explicit-locking.html). Это основания технического выбора, а оценки часов ниже — собственная предварительная оценка проекта.

Личные кабинеты, документы, сообщения и файлы нельзя отдавать из общего публичного кеша. Публичные API возвращают только специально выбранные поля. Email, телефон, дата рождения и доказательства экспертизы не попадают в публичный профиль. Шифрование контактов и способ поиска по email проектируются вместе с управлением ключами, ротацией и резервированием ключей.

| Встречи | availability_rules, slot_occurrences, bookings | Правила в часовом поясе IANA, конкретные встречи в UTC; запрет двойной записи и пересечения |
| Общение | conversations, conversation_members, messages, reports | Чтение только участниками беседы и уполномоченным администратором по процедуре |
| Результаты | results, artifacts, feedback, showcase_publications, publication_consents | Единственный итог на участие; отдельное согласие на каждый публикуемый материал |
| Автоматизация | notification_outbox, notifications, job_runs, audit_events | Повторные попытки, журнал ошибок, ключи идемпотентности |
| Расширение | learning_resources, ai_recommendations, ai_reviews, point_events, badge_awards, nominations, certificates | Версия модели и критериев, ручное решение; одно начисление на событие |

Окончательные поля, индексы и ограничения входят в спецификацию E1. Направления и причины настраиваемы, а допустимые переходы статусов задаются проверенными правилами сервера. Добавление произвольного статуса через справочник не должно создавать обход бизнес-правил.

## Контракт серверных действий

Это предлагаемая структура API для спецификации E1. Точные пути, поля и коды ошибок будут оформлены до реализации. Проверки доступа выполняются на сервере; исходные правила и критерии каждого действия связаны с задачами BACKLOG.md.

| Группа | Действия | Проверки |
|---|---|---|
| Вход | Запросить код, подтвердить, получить сессию, выйти, отозвать сессии | Срок кода, лимит попыток, подтверждённый email |
| Мой аккаунт | Получить профиль, сохранить анкету, подать на проверку, изменить язык и часовой пояс | Собственный пользователь; обязательные поля и согласия |
| Документы | Получить обязательный пакет и версию, подтвердить, получить историю, запросить копию | Пакет по роли и направлениям; неизменяемая опубликованная версия |
| Каталог | Получить направления и одобренные профили, поиск и фильтры | Только разрешённые публичные поля и действующие фильтры |
| Проекты | Создать и обновить, подать на публикацию, получить публичную часть или закрытые материалы, управлять командой | Автор, роль, модерация, членство, NDA и согласия |
| Заявки | Подать, отозвать, принять или отклонить | Допуск, отсутствие дубля, вместимость, причина отказа |
| Переписка | Получить беседы и сообщения, отправить сообщение, подать жалобу | Членство в беседе и ограничение частоты |
| Встречи | Сохранить расписание, получить слоты, забронировать, отменить, подтвердить, посмотреть историю | Временная зона, отсутствие пересечения, права сторон, транзакция |
| Участие и итог | Поставить на паузу, возобновить, завершить, приложить артефакт, оставить отзыв, подтвердить защиту | Допустимый переход, причина, инициатор, права на файл |
| Витрина | Запросить публикацию, выдать или отозвать согласие, одобрить публикацию | Подтверждённая защита и согласия владельцев материалов |
| Администрирование | Проверить анкету и контент, управлять документами, справочниками, ролями, жалобами и отчётами | Полномочия администратора, причина изменения и аудит |
| Автоматизация | Обработать очередь, напоминания, рекомендации ИИ и проверку человеком | Ограниченный служебный доступ, идемпотентность, журнал ошибки |

Для всех изменяющих действий задаём валидируемые входные данные, понятные ошибки, ограничения частоты там, где возможен спам, и защиту от повторного выполнения критических операций. Смена роли, приём на последнее место и запись на слот имеют отдельные контрольные сценарии.

## Этапы разработки

Оценка включает реализацию, обзор изменений и проверки своего этапа. E6 охватывает общую приёмку, подготовку запуска и восстановление после отказа. Правовые тексты, перевод и проверка бренда выполняются с участием владельца и соответствующих специалистов; ожидание их ответов может увеличить календарный срок.

|---|---|---|---|---|

| E1 | Репозиторий, локальная среда, схема данных, миграции, API-контракт, компоненты, три языка, тестовый сервер | E0 | Пустой проект запускается по инструкции; миграция создаёт базу; тестовая среда доступна | 30–45 |
| E2 | Вход, анкеты, документы и версии, журнал согласий, модерация, роли, направления | E1; документы и правила допуска | Менти и ментор проходят весь допуск; ограниченный пользователь не обходит его через API | 55–80 |

## Проверки и критерии готовности пилота

1. Менти, ментор и администратор проходят свои сценарии в тестовой среде; принятая регистрация требует подтверждённого email и полного актуального пакета документов.
2. Проверены права на чужие анкеты, проекты, заявки, сообщения, бронирования и файлы при прямом обращении к API. Администратор защищён усиленным входом.
3. Обновление обязательного документа ограничивает соответствующее действие до нового подтверждения; неподтверждённая анкета не публикуется. Старые версии и события остаются в истории.
4. Одновременная запись на один слот и принятие на последнее место дают одного победителя; повторный запрос не создаёт второй объект.
5. Часовые пояса, повторяющиеся слоты, отмена, изменение расписания и дата встречи корректны. Проверены зоны с переходом на летнее время, даже если пилот их не использует.
6. Успешное и досрочное завершение сохраняют обязательный итог и инициатора; отсутствие отзыва видимо; самостоятельный проект имеет определённого подтверждающего.
7. Отзыв согласия снимает кейс с витрины и прекращает публичную выдачу связанных материалов. Публичные API и кеши не раскрывают контакты или закрытые файлы.
8. KPI сверены на небольшой контрольной выборке независимо от интерфейса. Экспорт обезличен; маленькие группы не позволяют легко опознать человека по косвенным признакам.
9. Основные сценарии читаемы на мобильном экране, доступны с клавиатуры и работают на RU, KZ и EN. Проверены русские и казахские буквы, сообщения ошибок, даты и длинные тексты.
10. Загрузка файлов ограничена, вложения проверяются, секреты отсутствуют в клиентском коде и журналах. Письма, коды и очередь отправок устойчивы к повторным попыткам.
11. Тестовая нагрузка для пилота, резервное копирование и восстановление проверены. Предлагаемый ориентир нагрузки: 50 одновременных тестовых сессий; p95 типовых API-запросов до 1 секунды без внешних email и LLM, корректность записей без ошибок. Ориентир уточняется под выбранную среду.
12. У владельца есть рабочие инструкции, контакты поддержки, юридические тексты, переводы и брендовые материалы; выполнено решение о запуске. Открытых дефектов, нарушающих допуск, приватность, запись или фиксацию результата, нет.

Для будущей эксплуатации предлагаются ежедневные копии с проверенным восстановлением, целевая потеря данных не более 24 часов и восстановление до 4 часов. Владелец выбирает значения после оценки цены и рисков; требуемые показатели фиксируются в E6. Сама схема копирования должна включать базу, файлы и необходимые ключи.

## KPI и доступная мощность пилота

Цели из раздела 5 Word: 30–50 менти, 10–15 менторов, не более одного часа ментора в неделю, не менее 60 процентов команд до результата, 100 процентов структурированных завершений, публичных карточек и обязательных согласий, не менее 10 защищённых кейсов. Период набора менторов требует уточнения.

| Метрика | Предлагаемое определение для реализации |
|---|---|
| Активные пользователи | Одобренные аккаунты с определённой полезной активностью за утверждённое окно; отдельно от числа аккаунтов Active |
| Успешность проектов | Защищённые проекты выбранной когорты / проекты этой когорты, начавшие работу; окно наблюдения фиксируется |
| Полнота итогов | Завершённые участия с допустимой причиной и инициатором / все завершённые участия |
| Подписанные документы | Допущенные пользователи с полным актуальным обязательным пакетом / все допущенные пользователи; пакеты по ролям и направлениям |
| Публичность | Опубликованные карточки / карточки, прошедшие модерацию; приватные вложения не входят в показатель |
| Работа менторов | Фактические минуты проведённых встреч по неделе; время на сообщения учитывается отдельно, если владелец требует полный учёт |
| Набор менторов | По отдельным событиям открытия и принятия группы в утверждённом периоде |
| Витрина | Уникальные подтверждённые проекты с действующим согласием на публикацию |
| CSAT и NPS | Отдельные вопросы и формулы; NPS равен доле оценок 9–10 минус доле 0–6 на шкале 0–10; отсутствующие ответы исключаются, число ответов показывается |

Последние определения — предложения, которые нужно согласовать. В исходнике нет однозначного окна для активности или знаменателя всех метрик.

При двух слотах по 30 минут 10–15 менторов дают 20–30 встреч в неделю. Для 30–50 менти этого недостаточно, если каждому обещать одну индивидуальную встречу еженедельно. До набора определяем частоту консультаций, групповые встречи и загрузку; такие обещания нельзя выводить только из числа пользователей.

## Эксплуатация и расходы

Участие пользователей бесплатно по бизнес-требованиям. Платформа требует оплаты или доступных квот инфраструктуры, рассылки, хранения файлов и ИИ. До выбора поставщиков проверяем регион хранения, условия использования, ограничения, доступность для организации и актуальную цену. Стоимость сейчас не определена.

Бюджет считаем отдельно: разовое оформление документов и дизайна; ежемесячные сервер, база, копии, файлы, письма, наблюдение; переменный расход ИИ; домен; возможная подпись; платёжный провайдер при R2. Для пилота задаём денежный лимит, ограничения файлов и LLM, уведомление о приближении к бюджету и возможность отключить ИИ без остановки основного продукта.

Назначенный администратор проверяет новые анкеты, проекты и жалобы. Ему нужны сроки реакции, правила эскалации, возможность исправить результат, журнал действий и инструкции по ошибкам уведомлений. Разработчик отвечает за исправления и техническую эксплуатацию; решения по программе принимает владелец.

## Пилот и последующее расширение

После технической готовности R0 запускаем закрытую проверку с 5–10 приглашёнными тестовыми пользователями. По итогам исправляем проблемы допуска, заявок и встреч. Затем открываем один или несколько согласованных направлений для 30–50 менти и 10–15 менторов. Набор и длительность программы утверждает владелец; они не включены в срок создания приложения.

Предлагаю отдельные 4–6 недель наблюдения после открытия пилота. Еженедельно рассматриваем неоконченные регистрации, очередь модерации, принятие заявок, отмены и пропуски встреч, завершения и расходы. Для итоговых 10 кейсов может потребоваться более длинный цикл программы. R1 можно разрабатывать во время пилота, если это не задерживает исправление критических ошибок.

Расширение направлений проводится через справочник: название и переводы, фильтры, пакет документов, требования анкеты, оформление и проверка отображения. Новое направление не получает копию отдельного приложения. Рост нагрузки проверяется измерениями и дополнительным нагрузочным испытанием перед увеличением аудитории.

## Порядок работы

На неделю выбираем один завершённый сценарий и несколько связанных задач BACKLOG.md. Состояния задач: не начато, в работе, на проверке, готово либо блокировано с конкретной причиной. «Готово» требует реализации, применимой проверки, демонстрации и сохранённых доказательств результата.

Изменения бизнес-требований заносим в журнал решений до реализации. В конце недели показываем работающий путь, фиксируем обнаруженные ошибки и пересчитываем следующие задачи. Не держим одновременно много незаконченных модулей. Полезный результат каждой итерации — сценарий, который можно пройти в тестовой среде.

## Первые действия после планирования

1. Начать E0: заполнить журнал решений по аудитории, публичности, статусам, методу подписания и названию продукта; назначить владельцев документов и переводов.
2. Согласовать брендовые исходники и мультиязычную типографику; подготовить главную, анкету, каталог, карточку проекта и кабинет администратора как первые макеты.
3. Уточнить модель заявки, команды, участия и результата; составить API-контракт и список ограничений базы.
4. Создать рабочую основу приложения, тестовую среду и миграции E1.
5. Реализовать первый сквозной сценарий E2: регистрация менти → email → анкета → документы → решение администратора → доступ к кабинету.

План готов для начала разработки. Окончательные даты, стоимость поставщиков и юридическая процедура будут закреплены по мере принятия перечисленных решений.
