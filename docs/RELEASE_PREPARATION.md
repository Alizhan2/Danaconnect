# Подготовка выпуска для Vercel

2 октября 2026 года. Пользователь выбрал Vercel. Подключение аккаунта пока возвращает требование повторной авторизации; публичного выпуска нет. Этот документ описывает подготовленные инструменты и порядок работы после подключения ресурсов.

## Состав выпуска

- Пользовательский сайт, отдельная админка, API и зафиксированные миграции.
- Отдельная конфигурация Vercel с внешней PostgreSQL, приватными файлами, почтой и выбранным обработчиком очереди.
- Шрифт DejaVu Sans 2.37 с исходной лицензией для сертификатов RU/KZ/EN. Проверена таблица символов; сертификат в облаке ещё не выдавался.
- Архив исходников с контрольными суммами. Он не содержит установленных зависимостей, собранных приложений, локальной базы, загруженных файлов или приватных `.env`.

## 1. Подготовить закрытые настройки

Из корня проекта, с установленными зависимостями:

```powershell
.\.venv\Scripts\python.exe deploy/vercel_config.py generate --output deploy/.env.vercel.local
```

Новый файл создаётся без перезаписи существующего и получает новые ключи. Владелец или оператор заполняет реальные параметры в закрытом редакторе. Для worker используются **те же** ключи, база и провайдеры; повторная генерация ключей для уже существующей базы не нужна. Preview получает отдельные ресурсы и секреты.

```powershell
.\.venv\Scripts\python.exe deploy/vercel_config.py validate --env-file deploy/.env.vercel.local
```

Эта команда проверяет только структуру настройки и не подключается к провайдерам. Она не подтверждает права на bucket, получение писем, доступность базы или работающий планировщик. Настройки переносятся в защищённое окружение проекта после подключения аккаунта; секреты не размещаются в `NEXT_PUBLIC_*`. Единственное публичное поле шаблона — `NEXT_PUBLIC_WEB_URL`, адрес пользовательского сайта для ссылок админки.

## 2. Подготовить обновление внешней базы

Сначала согласовать окно обновления и резервную копию у провайдера. Указать подключение PostgreSQL, пригодное для миграций. Проверка версии, транзакционная блокировка и применение используют одно соединение; transaction pooler не должен прерывать эту транзакцию. Остановить другие процессы миграции: самостоятельный запуск Alembic не учитывает блокировку этого инструмента. Обновление не создаёт копию базы автоматически. Передача соединения реализована по [рецепту Alembic](https://alembic.sqlalchemy.org/en/latest/cookbook.html#sharing-a-connection-across-one-or-more-programmatic-migration-commands).

Инструмент по умолчанию показывает локальный план зафиксированных миграций. Он не обращается к базе и не подтверждает её текущую версию:

```powershell
.\.venv\Scripts\python.exe deploy/migrate_external.py
```

Применение — отдельное явное действие с заполненным закрытым файлом и заранее известной текущей версией. Для новой пустой базы используется `empty`; для существующей — её точный Alembic revision. Пример первой установки:

```powershell
.\.venv\Scripts\python.exe deploy/migrate_external.py --env-file deploy/.env.vercel.local --expected-current empty --apply
```

Перед изменением инструмент сверяет фактическую версию, для новой базы проверяет отсутствие пользовательских объектов, затем обновляет только до текущего head из проекта. Seed и автоматический downgrade не выполняются. Откат данных описан в [облачной инструкции](CLOUD_RUNBOOK.md), а не в этом инструменте.

## 3. Подключить приложения и очередь

Корень проекта Vercel — корень репозитория. Его Services направляют `/api` в API, `/admin` в админку, остальные страницы в сайт. Полный порядок и варианты worker находятся в [CLOUD_RUNBOOK.md](CLOUD_RUNBOOK.md).

API включает `assets/fonts/**` в функцию с entrypoint `app/main.py`. Такой ключ функции и включение дополнительных файлов заданы по [FastAPI reference](https://vercel.com/docs/frameworks/backend/fastapi) и [functions configuration](https://vercel.com/docs/project-configuration/vercel-json#functions). Фактический состав облачной функции требует подтверждения после развёртывания.

В режиме Vercel API требует явно выбранные production settings и загрузки не больше 3 MiB. Соединения SQLAlchemy не сохраняются в локальном пуле между запросами (`NullPool`); внешний pooler и лимит соединений настраиваются у провайдера. Это не гарантия нагрузочной готовности. Механизм отключения пула: [SQLAlchemy](https://docs.sqlalchemy.org/en/20/core/pooling.html#switching-pool-implementations). Индикатор среды описан в [Vercel system variables](https://vercel.com/docs/environment-variables/system-environment-variables); шаблон явно задаёт его и для операторских процессов.

## 4. Зафиксировать исходники

```powershell
.\.venv\Scripts\python.exe deploy/package_release.py --output artifacts/danaconnect-source-20261002.zip
```

Повторный выпуск записывается под новым именем. `RELEASE_MANIFEST.json` внутри архива перечисляет SHA-256 каждого исходного файла и общий отпечаток состава. Это архив исходников, из которого зависимости и приложения ещё нужно собрать. Контрольные суммы фиксируют состав; функциональная приёмка и публикация ими не подтверждаются.

## Оставшиеся действия

Подключить аккаунт Vercel, выбрать внешние PostgreSQL/S3/почту и способ работы очереди. Затем применить настройки и миграции, настроить MFA администратора, опубликовать утверждённые документы и провести согласованную приёмку перед приглашением участников. Аккаунты, платные ресурсы, внешние данные и письма на этом этапе не создаются инструментами автоматически.
