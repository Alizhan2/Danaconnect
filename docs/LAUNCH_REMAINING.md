# DanaConnect: оставшиеся шаги запуска

**Обновлено 3 октября 2026, Asia/Oral.** Основание: [проверка и публикация](VERIFICATION_2026-10-02.md), [мобильная приёмка](VERIFICATION_2026-10-03.md), [состояние реализации](IMPLEMENTATION_STATUS.md). Это список незавершённых действий; он не разрешает публикацию черновиков или согласия за участников.

## Уже подтверждено

Vercel Production и HTTPS опубликованы; Neon PostgreSQL отвечает с миграцией `0e82eab8e5ef`. SMTP прошёл STARTTLS/AUTH, существующее письмо рабочего отправителя найдено во входящих. Private Blob прошёл запись/чтение/удаление отдельного файла и отказ анонимному доступу. QStash активен; успешный цикл worker наблюдался. Пройдены 102 API-теста, 22 frontend-проверки, обе сборки и 54 облачные HTTP-проверки после публикации. Подключать эти сервисы заново по старым пометкам «не проверено» не требуется.

## Порядок до ограниченного пилота

| Шаг | Кто завершает | Что сделать | Критерий завершения |
|---|---|---|---|
| 1. Оператор и условия | Владелец | Подтвердить фактические реквизиты и адрес для обращений, аудиторию/возраст, условия участия и модерации, ответственность команды, права использования бренда. В черновиках остаются поля для утверждения. | Есть согласованная версия условий с настоящими реквизитами; адреса и юридические обязательства не выдуманы. |
| 2. Обработка и хранение данных | Владелец с ответственным за данные; техническую реализацию готовит разработчик | Согласовать фактических провайдеров/места хранения и передачи, сроки хранения, удаление, резервные копии и доступ команды. Полный аудит соответствия текущей облачной схемы не подтверждён. | Утверждён порядок обработки и технические изменения, если нужны; тексты соответствуют фактической инфраструктуре. |
| 3. Обязательные документы | Владелец утверждает, администратор публикует | Завершить правила, политику данных и согласие, проверить RU/KK/EN и применимость. Если запускаются закрытые материалы, отдельно согласовать документ для `private_project`; наличие трёх черновиков не означает готовность этого контекста. | В `/admin/documents` опубликованы утверждённые актуальные версии; для нужной роли/направления `/me/registration-requirements` возвращает готовность. Каждый участник лично подтверждает версии перед отправкой анкеты. |
| 4. Доступ команды | Каждый администратор | Подключить собственный Authenticator по закрытому QR, пройти email OTP → TOTP → админку. Подтвердить состав команды и объём доступа. Сейчас `admin` имеет полный доступ; ограниченная роль координатора не реализована. | Рабочий вход каждого администратора подтверждён без передачи его кодов и согласий агенту. QR и ключи остаются закрытыми. |
| 5. Интерактивная приёмка | Разработчик; реальные согласия выполняют участники | В изолированной базе пройти регистрацию и документы, модерацию, каталог, заявку/принятие, диалог, закрытый файл, встречу/отмену, результат, поддержку, privacy. Проверить мобильные экраны и три языка; рабочий путь сверить после утверждения документов. | Сохранён отчёт реальных браузерных действий; HTTP 200 и unit tests не подменяют прохождение форм. |
| 6. Почта сценариев | Разработчик и согласованный получатель | Проверить доставку приглашения и напоминания, expiry, задержку очереди и обработку ошибки. Существующее OTP-письмо подтверждает один входящий случай; SMTP AUTH не доказывает все типы писем. | Согласованный получатель подтвердил нужные письма; операции не отправляют сообщения посторонним людям без разрешения. |
| 7. Восстановление и нагрузка | Разработчик; владелец определяет цели | Восстановить резервную копию в отдельную базу, проверить защищённые файлы и согласованную нагрузку/конкуренцию PostgreSQL. Определить допустимые потерю данных и время восстановления. | Восстановленная отдельная база проверена; рабочая база не перезаписана. Есть результаты для согласованного числа участников. |
| 8. Эксплуатация | Владелец назначает ответственных, разработчик готовит процедуры | Назначить поддержку и ответственного за privacy/удаление, контроль очереди/worker, backup и ротацию секретов. Установить порядок действий при сбое; UI не разрешает фиктивно завершать erase. | Назначены ответственные и порядок восстановления/удаления; первый пилот ограничен согласованной аудиторией. |

**Основной текущий блокер отправки анкет — шаги 1–3.** Локальные юридические черновики не опубликованы и не утверждены. Чекбоксы или тестовые согласия в изолированной базе не снимают этот блокер.

## Опциональные подключения

Продвижение по шагу 5: перечисленные локальные формы уже пройдены — [браузерный отчёт](BROWSER_VERIFICATION_2026-10-02.md). [Дополнение 3 октября](VERIFICATION_2026-10-03.md) подтверждает мобильные сообщения/меню, календарь, privacy, результаты админки, закрытый файл и отзыв/восстановление витрины. Пройдены 118 API и 58 frontend проверок. Остаются сохранение JSON/ICS из браузера, остальные не перечисленные экраны и полный прогон рабочей среды после утверждения документов.

- **Google для всех:** завершить Branding и Audience в существующем Google Auth Platform, затем проверить реальный вход. Сейчас режим Testing ограничивает аккаунты. Вход администратора по Google намеренно не предусмотрен: ему нужны email и MFA. Открытый Google-вход не является условием начала пилота через email.
- **Автопубликация:** связать существующий GitHub аккаунт с Authentication Vercel и подключить репозиторий/production branch. CI с тестами уже работает, публикация пока через CLI. Новый проект не требуется.
- **Собственный домен, AI, платежи, видеоконференции и внешние календари:** выбрать только при отдельной потребности. Для следующего шага не создаются новые платные ресурсы; AI отключён.

## Как читать админские сигналы

- `/admin/operations` показывает снимок на время запроса, а не постоянное наблюдение. Свежесть worker — успешный цикл менее пяти минут назад; ручное обновление даёт новое наблюдение.
- Наличие email/storage/Google настройки не равно успешному пользовательскому сценарию. Для SMTP/Blob/QStash отдельные подтверждения уже записаны в отчёте.
- `legal_documents_configured` в operations требует глобальные опубликованные документы регистрации для менти и ментора и частного проекта для ментора. Применимость к конкретному участнику отдельно проверяет `/me/registration-requirements`.
- В `/admin/launch` ручные пункты помечаются «не подтверждено» статически: сохранения акта приёмки на этой странице нет. Этот текст не отменяет результаты отчёта и не означает сбой почты или файлов.
